# Пользовательский форк HAPI

Это поддерживаемый форк [HAPI](https://github.com/tiann/hapi) для локальной работы с агентами из терминала на компьютере и с телефона через Web/PWA. Он сохраняет архитектуру upstream — агенты, Hub и Web/PWA — и меняет навигацию по сессиям, запуск проектов, инструменты ревью и обмен сообщениями.

Полное описание продукта, поддерживаемых агентов и архитектуры находится в **[каноническом README upstream](https://github.com/tiann/hapi#readme)**. Здесь перечислены только отличия и правила эксплуатации этого форка.

## Что изменено в форке

| --- | --- | --- |
| Навигация по сессиям | Отдельные разделы Working, Active, keepalive-only Idle и Recent; стабильная сортировка по активности; непрочитанные ответы; закрепление внутри проекта и глобально; скрытие неактивных сессий; подписи проекта и Git-ветки; массовое удаление HAPI-сессий проекта с сохранением локальных транскриптов агента. | Нужные сейчас сессии остаются на виду с понятным контекстом проекта, а тихие подключённые процессы и старые сессии не заслоняют текущую работу. |
| Проекты и новые сессии | Поиск, сортировка и закрепление корней рабочих пространств, ручной выбор папки, продолжение существующей сессии в другой разрешённой папке, Codex первым в списке и первый настроенный корень как начальная директория. | Runner, ограниченный общей папкой с проектами, позволяет запускать или продолжать Codex в любом разрешённом проекте без жёстко заданных путей. |
| Файлы и ревью | На экране Files поиск среди изменённых файлов отделён от поиска по всему проекту. В ответах агента могут отображаться сделанные им изменения, а прикреплённые DIFIT-ревью и merge request — в заголовке сессии. | С телефона видны незакоммиченные правки, изменения каждого ответа, полный результат работы в ветке и внешнее ревью без необходимости открывать каждый файл отдельно. |
| Настройки агентов и жизненный цикл | Новые сессии Codex изначально используют YOLO; последующий явный выбор запоминается. Stop, reopen, restart, восстановление после холодного запуска Hub и синхронизация истории Codex аккуратнее сохраняют состояние и время активности. Поддерживаемые агенты получают инструкцию поддерживать русские заголовки задач в соответствии с текущей целью; для Codex заголовок также можно перегенерировать из меню сессии. Главное эксплуатационное отличие — способ распространения: npm-пакеты, релизные бинарники и автообновление upstream устанавливают upstream HAPI, а не этот форк. Инструкции upstream для сборки нативных приложений здесь неприменимы.

## Установка и запуск форка

Ветка по умолчанию — `custom`. Для сборки из исходников нужен Bun 1.4.0:

```bash
git clone --branch custom https://github.com/WarLikeLaux/hapi.git
cd hapi
bun install --frozen-lockfile
bun run build:single-exe
```

Не используйте `npx @twsxtd/hapi` или релизные бинарники upstream, если ожидаете описанное выше поведение форка. Механизм смены версии runner умеет активировать установленный вами бинарник форка, но сам обновления форка не скачивает.

Для уже настроенной Linux-установки через пользовательские службы systemd в репозитории есть защищённая команда локального деплоя:

```bash
bun run deploy:local-hub
```

Она проверяет типы и тесты Hub, собирает встроенный веб-клиент, исполняемый файл HAPI и Telegram-коннектор, сохраняет предыдущие бинарники для отката, перезапускает Hub и настраивает будущие запуски runner на тот же бинарник форка. Для этого варианта кроме Bun нужен Go. По умолчанию ожидаются `hapi-hub.service`, `hapi-runner.service` и `~/.local/lib/hapi-custom/current/hapi`; их можно изменить через `HAPI_SERVICE_NAME`, `HAPI_RUNNER_SERVICE_NAME` и `HAPI_INSTALL_PATH`. Перед использованием на другом компьютере прочитайте [скрипт деплоя](scripts/deploy-local-hub.sh).

Общие инструкции upstream остаются применимы: [установка и переменные окружения](docs/guide/installation.md), [агенты](docs/guide/agents.md), [Web/PWA](docs/guide/pwa.md) и [уведомления](docs/guide/notifications.md).

### Опциональные чаты Telegram-аккаунта

Экран Chats использует отдельный MTProto-sidecar, а не Telegram-бота для уведомлений об агентах. Соберите его командой `bun run build:telegram-connector` и положите `connectors/telegram/hapi-telegram-connector` рядом с установленным исполняемым файлом HAPI; `deploy:local-hub` делает это автоматически. Затем интерфейс запросит API ID и hash с [my.telegram.org](https://my.telegram.org/apps), номер телефона аккаунта, код входа и, при необходимости, пароль 2FA.

Коннектор хранит учётные данные и MTProto-сессию с правами только для владельца внутри каталога данных HAPI. В HAPI кэшируются только диалоги, явно выбранные в интерфейсе. Разработка и использование нестандартного пути к бинарнику описаны в [инструкции коннектора](connectors/telegram/README.md).

## Безопасность и приватная конфигурация

- Не добавляйте в Git токены Hub, Telegram-бота, API-данные и сессии Telegram-аккаунта, публичные или приватные адреса, а также локальные пути.
- Просмотр рабочих пространств ограничен корнями, явно переданными через `hapi runner start --workspace-root <путь>`; без них доступна только домашняя папка пользователя runner, а не вся файловая система.
- Считайте YOLO опасным режимом: он обходит обычные подтверждения и ограничения песочницы агента, кроме явных execpolicy-правил `prompt` и MCP-сценариев, требующих реального ввода пользователя.
- Публикация Hub или включение Telegram по-прежнему требует аутентификации, TLS, туннеля и корректного `HAPI_PUBLIC_URL` по документации upstream. Локальный деплой сам по себе не делает публичный Hub безопасным.

Перед изменением аутентификации, пространств имён, исполнения команд, уведомлений, доступа к файлам, управления runner, внешних ссылок или релизных workflow прочитайте [SECURITY.md](SECURITY.md) и [политику синхронизации форка](FORK_SYNC.md).

## Обновление из upstream

Постоянные правила записаны в [FORK_SYNC.md](FORK_SYNC.md). Кратко: изменения из `upstream/main` проверяются и вливаются в `custom` через `--no-ff`; функции форка, границы безопасности, ограничения релизных workflow и тесты должны сохраниться. Поддерживаемую ветку нельзя перебазировать или публиковать через force-push.

## Лицензия и благодарности

HAPI означает «哈皮» — китайскую транслитерацию названия [Happy](https://github.com/slopus/happy). Исходный проект HAPI и его участники остаются авторами продукта; этот репозиторий поддерживает специализированную downstream-адаптацию.
